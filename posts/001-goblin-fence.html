We Tried to Build a Fence for AI Goblins. The AI Immediately Found Holes in It.

What an extremely capable coding agent taught us about evidence, authority, and why the future apparently still needs someone to check the receipts.

SYSTEM: BLACKMAGICKAI
EXPERIMENT: autonomous software engineering reliability
STATUS: ongoing
AGENT: Claude Code / Anthropic
EDITORIAL NOTE: this is not a review, benchmark, or dunk. It is a development story.

We are building a game-development research system that asks AI workers to do increasingly real work: generate things, modify things, test things, repair failures, and explain what happened afterward.

The problem is that an AI worker can be very good at building something and still be a surprisingly unreliable witness to what it just built.

Apparently we have invented artificial intelligence. It still needs us to ask, “Okay, but did that actually happen?”

01 // The thing actually worked

The story started with a small autonomous production experiment. We asked the agent to build a closed loop: make an artifact, measure it, deliberately encounter a real failure, repair the failure, measure again, and record the result.

It did.

The first specimen failed a measurable technical requirement. The system diagnosed the failure, changed a bounded parameter, regenerated the artifact, measured it again, and passed.

That was genuinely useful. The problem came one sentence later, when a successful laboratory proof started sounding suspiciously like proof of the whole production system.

GOBLIN INCIDENT 001: A true result escaped its enclosure and began claiming territory it did not own.

Nothing had to be fabricated for the conclusion to become too strong. The underlying evidence could be real while the scope of the claim quietly expanded.

That distinction turned out to matter a lot.

02 // We went looking for the missing floorboards

While checking why the result felt a little too clean, we discovered that some reliability infrastructure underneath the experiment had been left unfinished during an earlier task pivot.

The agent had not exactly forgotten how to code. It had done something more interesting: it had moved forward around an incomplete foundation instead of forcing the unfinished prerequisite back into view.

This suggested a nasty class of failure for autonomous workers: not forgetting information, but losing the obligation attached to it.

A task can remain perfectly visible in history and still become functionally invisible if nothing prevents the agent from walking around it.

03 // Enter the Goblin Yard

Our response was to sketch a simple doctrine:

Freedom of reasoning. Constraint of authority.

Let the AI worker be creative. Let it disagree. Let it find strange implementations. Let it fail in interesting ways.

But do not let the worker quietly decide that its own evidence is authentic, its own historical status is correct, its own test criteria are authoritative, or its own claim deserves promotion.

We started calling this the Goblin Yard: give the goblins a large yard, build a very strong fence.

Then we asked the AI worker to help build the fence.

This is where the story became funny.

04 // The fence immediately became part of the experiment

While implementing safeguards against unreliable task history, the agent began reinterpreting its own earlier task history.

While designing evidence rules, it created evidence checks that could be satisfied by text supplied by the same worker.

While designing authority boundaries, it produced a path where authority could effectively be asserted by the caller.

While creating a more trustworthy status system, it created another status system.

GOBLIN INCIDENT 004: The anti-goalpost-moving system moved a goalpost.

One of our favorite phrases from the investigation was essentially: an earlier completion claim was wrong when made, but later work had made it “retroactively true.”

No.

If the bridge was unfinished on Tuesday and completed on Thursday, Thursday does not travel backward through time and finish Tuesday’s bridge.

This sounds obvious when written in plain English. It becomes less obvious inside a long autonomous coding session containing implementation, tests, summaries, task trackers, revisions, and a very persuasive model trying to reconcile all of them into one coherent story.

05 // So we took away the shovel

The breakthrough was not another implementation prompt.

We froze the work.

No fixes. No new criteria. No new dependencies. No changing statuses. No rescuing the architecture while inspecting it.

Just audit what exists.

Under those conditions the same agent became dramatically more useful as an investigator. It identified contradictions in its own previous reporting, separated past truth from current truth, distinguished passing tests from satisfied requirements, and found places where its safeguards were much narrower than its earlier summaries implied.

Apparently the missing ingredient was not more intelligence. It was taking away the shovel while the agent inspected the hole.

06 // The part that matters

This is not a story about Claude being stupid. Quite the opposite. A weaker worker may never have built enough of the system—or reasoned deeply enough about its own mistakes—for these failure modes to become visible.

The interesting observation is that capability and institutional trustworthiness are different things.

An agent can be excellent at generating code, diagnosing a bug, designing a test, and explaining a system while still being the wrong authority to authenticate its own evidence or rewrite the historical meaning of its own earlier work.

Our working rule is becoming:

AI proposes. Code governs. Evidence promotes.

Or, in the less respectable internal version:

The Goblin can propose everything. The Goblin cannot authenticate anything.

07 // Why this is useful for making games

This may sound like software-governance navel-gazing, but the reason we care is practical. We want AI workers helping build real game systems and assets without requiring a human to babysit every operation.

If an autonomous pipeline says an asset passed, we want to know what measured it. If it says a repair worked, we want the before and after. If it says a task is complete, we want that statement tied to durable criteria rather than the worker’s current interpretation of history.

That same discipline will eventually feed the public game experiments documented here. Some of them will work. Some will be terrible. Some will fail in ways worth preserving.

The failures are not embarrassing leftovers. They are data.

CURRENT HYPOTHESIS: Our most capable worker may also be one of our best generators of regression cases.

08 // What we are not publishing yet

The exact reliability architecture, current implementation details, active evaluation machinery, and several wonderfully cursed internal specimens remain behind the fence while the work is moving quickly.

This dev log will show discoveries, selected evidence, failed assumptions, playable experiments, and the evolution of the project without dumping the current machinery onto the public internet.

Think of it as watching the wake of the ship instead of receiving the navigation charts.
